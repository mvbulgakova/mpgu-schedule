# Architecture Review: МПГУ Расписание

**Дата:** 2026-05-22  
**Автор:** AI Code Review  
**Статус:** Черновик для обсуждения

---

## Executive Summary

Проект представляет собой serverless-архитектуру для сбора и отображения расписания занятий МПГУ. Система состоит из скрапера (Python), PWA (React + TypeScript) и CI/CD (GitHub Actions). Данные хранятся в Git-ветке `data`.

**Общая оценка:** Архитектура работоспособна для текущего масштаба (~400 групп, 16 институтов), но содержит несколько критических точек отказа и технических долгов, которые станут проблемами при масштабировании.

---

## 1. Критические точки отказа

### 1.1. Зависимость от GitHub raw.githubusercontent.com

**Проблема:** PWA читает данные напрямую с `raw.githubusercontent.com`. Это создаёт несколько рисков:

| Риск | Вероятность | Влияние |
|------|-------------|---------|
| Rate limiting GitHub API | Средняя | Блокировка доступа для пользователей |
| Изменение формата URL GitHub | Низкая | Полный отказ PWA |
| Блокировка домена в РФ | Средняя | Недоступность для части пользователей |
| CDN downtime | Низкая | Временная недоступность данных |

**Текущее состояние:**
```typescript
// pwa/src/services/scheduleApi.ts
const BASE = __DATA_BASE_URL__; // https://raw.githubusercontent.com/.../data
```

**Рекомендации:**
1. **Приоритет 1:** Добавить Cloudflare Workers или Vercel Edge Function как прокси-слой между PWA и GitHub
2. **Приоритет 2:** Реализовать fallback на зеркало данных (например, S3 bucket)
3. **Приоритет 3:** Рассмотреть перенос данных в отдельный CDN с кастомным доменом

---

### 1.2. Отсутствие бэкенда для агрегации данных

**Проблема:** PWA загружает полный `schedule.json` института (до 79 групп × 2 недели × 7 дней × ~8 занятий = ~8000 уроков). При открытии группы все данные парсятся на клиенте.

**Метрики:**
- `philology/schedule.json`: ~2.4 MB uncompressed
- Время парсинга на мобильном устройстве: 300-800ms
- Потребление памяти: ~15-25 MB

**Рекомендации:**
1. Генерировать pre-filtered JSON per group в скрапере
2. Или добавить лёгкий API layer (Cloudflare Workers, ~$5/мес)

---

### 1.3. Gemini API как единая точка отказа для image-based PDF

**Проблема:** Институты `preschool`, `languages`, `childhood` частично используют image-based PDF. Без `GEMINI_API_KEY` данные не извлекаются.

**Текущее состояние:**
```json
// plan.md статусы
"preschool": "⚠️ мало (image PDF)",
"languages": "⚠️ мало (image PDF)",
"childhood": "❌ sub_faculties не обходятся"
```

**Риски:**
- Лимиты API (15 запросов/мин для бесплатного тарифа)
- Изменение формата ответа Gemini
- Блокировка API ключа

**Рекомендации:**
1. Добавить Tesseract OCR как fallback (бесплатно, но медленнее)
2. Кэшировать результаты парсинга image-based PDF на уровне файлов
3. Рассмотреть платный тариф Gemini (~$2-5/мес для текущего объёма)

## 2. Edge Cases и граничные случаи

### 2.1. Расписание ЗФО (заочная форма)

**Статус:** ❌ Не поддерживается

**Проблема:** Заочники используют даты вместо дней недели (`15.09.2025`, `16.09.2025`). Текущая модель данных предполагает фиксированные дни недели.

**Влияние:** ~15-20% студентов не видят своё расписание

**Рекомендация:** 
```typescript
// Новая структура для ЗФО
interface ZaoLesson extends Lesson {
  date: string; // "2025-09-15"
  is_session_period: boolean;
}

interface ZaoGroup {
  name: string;
  form: "correspondence";
  schedule: {
    sessions: Array<{
      period_start: string;
      period_end: string;
      days: DaySchedule;
    }>;
  };
}
```

---

### 2.2. Дублирующиеся группы в нескольких файлах

**Статус:** ⚠️ Частично решено

**Текущее решение:** `_merge_duplicate_groups()` в `main.py` объединяет по `time_start + subject`.

**Проблема:** Если одна группа имеет разные аудитории/преподавателей в разных файлах — данные теряются.

**Пример:**
```json
// Файл 1
{"time_start": "11:00", "subject": "Математика", "room": "А-101"}
// Файл 2
{"time_start": "11:00", "subject": "Математика", "room": "Б-205"}
// Результат: только один урок сохранится
```

**Рекомендация:** Объединять по полному ключу `(time_start, subject, day, week)` с приоритетом более свежего файла.

---

### 2.3. Подгруппы (subgroup)

**Статус:** ❌ Не реализовано

**Проблема:** Парсер видит маркеры `(п/г 1)`, `(п/г 2)`, но всегда записывает `subgroup: null`.

**Влияние:** Студенты не видят, какая подгруппа куда идёт

**Где теряется:**
- `parsers/pdf_parser.py`: не парсит суффиксы подгрупп
- `normalizer/schedule_normalizer.py`: `normalize_lesson_type()` не извлекает subgroup

**Рекомендация:**
```python
# normalizer/schedule_normalizer.py
def normalize_subgroup(text: str) -> int | None:
    if re.search(r'п/г\s*1|подгруппа\s*1', text, re.IGNORECASE):
        return 1
    if re.search(r'п/г\s*2|подгруппа\s*2', text, re.IGNORECASE):
        return 2
    return None
```

---

### 2.4. Переход на летнее/зимнее время

**Статус:** ❌ Не обработано

**Проблема:** Россия не переходит на летнее время, но если университет решит изменить сетку времени — все `time_start`/`time_end` станут неверными.

**Рекомендация:** Хранить `slot` как первичный ключ, а время вычислять из централизованной конфигурации:
```json
// meta/time_slots.json
{
  "slots": [
    {"slot": 1, "start": "09:00", "end": "10:35"},
    {"slot": 2, "start": "11:00", "end": "12:35"}
  ],
  "effective_from": "2025-09-01"
}
```

## 3. Технический долг

### 3.1. Обработка ошибок в PWA

**Проблема:** При ошибке загрузки данных PWA показывает статичное сообщение без возможности retry.

**Текущий код:**
```tsx
// App.tsx
{!indexLoading && !cachedIndex && (
  <div>Не удалось загрузить данные. Проверьте соединение.</div>
)}
```

**Рекомендация:**
```tsx
<button onClick={() => queryClient.invalidateQueries(['index'])}>
  Попробовать снова
</button>
```

---

### 3.2. Отсутствие версионирования API

**Проблема:** PWA жёстко привязан к текущей структуре `schedule.json`. Любое изменение формата сломает всех пользователей.

**Рекомендация:**
```json
// schedule.json
{
  "version": "1.0",
  "schema_url": "https://mpgu-schedule.github.io/schema/v1.json",
  ...
}
```

```typescript
// pwa/src/services/scheduleApi.ts
if (data.version !== SUPPORTED_VERSION) {
  showUpgradeNotice();
}
```

---

### 3.3. Hardcoded пути в скрапере

**Проблема:**
```python
# scraper/main.py
CONFIG_PATH = Path(__file__).parent / "config" / "institutes.json"
DATA_PATH = os.environ.get("DATA_PATH", "./data")
```

**Риск:** При изменении структуры репозитория скрапер перестанет работать.

**Рекомендация:** Использовать `pkg_resources` или относительные пути от корня проекта.

---

### 3.4. Missing type safety в Python

**Проблема:** Скрапер написан без type hints, что усложняет рефакторинг.

**Рекомендация:** Добавить mypy и typing:
```python
from typing import TypedDict, Literal

class Lesson(TypedDict):
    slot: int | None
    time_start: str
    # ...
```

## 4. Масштабируемость

### 4.1. Что будет при 500+ группах?

**Текущие метрики:**
- 16 институтов → ~400 групп
- Средний размер `schedule.json`: 1.2 MB
- Время сборки PWA: ~15 сек

**Прогноз при 50 институтах / 1500 группах:**
- Размер данных: ~10-15 MB
- Время первой загрузки PWA: 3-5 сек на 3G
- GitHub Actions timeout: риск превышения 60 мин

**Рекомендации:**
1. **Сегментация данных:** Разбить `schedule.json` на файлы по группам
2. **Ленивая загрузка:** PWA загружает только выбранный институт
3. **Инкрементальный деплой:** Обновлять только изменившиеся файлы

---

### 4.2. Что будет при 50+ институтах?

**Проблема:** `institutes.json` требует ручного добавления каждого института.

**Рекомендация:**
1. Автоматическое обнаружение институтов через краулинг `mpgu.su/ob-mpgu/struktura/`
2. Конфигурация через PR от представителей институтов

## 5. Безопасность

### 5.1. API ключи в CI/CD

**Текущее состояние:**
```yaml
# .github/workflows/scrape.yml
env:
  ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

**Риски:**
- Компрометация токена GitHub → доступ к API ключам
- Отсутствие ротации ключей

**Рекомендации:**
1. Включить двухфакторную аутентификацию для всех контрибьюторов
2. Настроить автоматическую ротацию ключей каждые 90 дней
3. Использовать OIDC для доступа к облачным API вместо долгоживущих токенов

---

### 5.2. XSS через расписание

**Проблема:** Данные из PDF попадают напрямую в DOM без санитизации.

**Пример атаки:**
```
Subject: "<img src=x onerror=alert('XSS')>"
```

**Текущая защита:** React автоматически экранирует текст в `{variable}`.

**Рекомендация:** Добавить явную санитизацию для полей с HTML-подобным контентом:
```typescript
import DOMPurify from 'dompurify';
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(subject) }} />
```

---

### 5.3. Dependency vulnerabilities

**Проблема:** Устаревшие зависимости в `package.json` и `requirements.txt`.

**Рекомендация:**
```bash
# PWA
npm audit fix
npx npm-check-updates -u

# Scraper
pip install pip-audit
pip-audit -r requirements.txt
```

Настроить Dependabot для автоматических обновлений.

## 6. Вопросы для обсуждения

### 6.1. Стоит ли добавлять бэкенд?

**Аргументы за:**
- Централизованное кэширование
- Агрегация данных на сервере
- Push-уведомления
- Аналитика использования

**Аргументы против:**
- Усложнение архитектуры
- Необходимость хостинга (~$10-50/мес)
- Требует DevOps компетенций

**Предложение:** Начать с Cloudflare Workers (~$5/мес, serverless)

---

### 6.2. Нужно ли хранить историю расписаний?

**Текущее состояние:** Ветка `data` хранит только актуальное состояние.

**Аргументы за историю:**
- Откат при ошибках парсинга
- Анализ изменений расписания
- Юридические требования (споры со студентами)

**Аргументы против:**
- Увеличение размера репозитория
- Усложнение логики скрапера

**Предложение:** Хранить снапшоты раз в неделю в отдельной ветке `data-history`

---

### 6.3. Поддержка Android/iOS приложений?

**Текущее состояние:** Есть заготовка `android/` с WebView.

**Вопросы:**
- Стоит ли развивать нативное приложение?
- Или достаточно PWA с установкой на домашний экран?

**Рекомендация:** PWA достаточно для 95% use cases. Нативное приложение оправдано только для push-уведомлений.

## 8. Заключение

Архитектура проекта демонстрирует хороший баланс между простотой и функциональностью для текущего масштаба. Однако отсутствие буферного слоя между данными и клиентами, неполная поддержка форматов расписаний и технический долг в обработке ошибок создают риски при росте пользовательской базы.

**Ключевая рекомендация:** Начать с добавления прокси-слоя (Cloudflare Workers) и поддержки подгрупп — это даст максимальный эффект при минимальных затратах.
